# struct-linter — линтер структуры проекта

Детерминированный CLI-линтер: проверяет структуру проекта по курируемому эталону и возвращает
машиночитаемый вердикт с однозначным кодом возврата. Контракт рассчитан на вызов даже слабой
моделью — достаточно пути к проекту и идентификатора эталона.

## Что делает линтер

Линтер обходит дерево проекта (только имена и пути, содержимое файлов не читается), применяет
правила эталона и печатает вердикт. Эталон — версионированные данные
([`templates/`](./templates)), а не логика в коде. Границы контракта заданы замкнутыми JSON Schema
([`schemas/`](./schemas)) с `additionalProperties: false`. Схемы и эталоны вкомпилированы в бинарь,
поэтому образ самодостаточен и не требует файлов данных на диске.

Проверяются четыре класса правил: обязательные пути, запрещённые пути, именование и разметка слоёв
по путям.

## Быстрый старт

Через Docker (проект монтируется только для чтения):

```bash
make struct-linter-build
docker run --rm -v "$PWD:/work:ro" struct-linter:local validate --template auto
```

Через обёртку [`tools/struct-linter/lint.sh`](./tools/struct-linter/lint.sh) — она собирает
`docker run` из явных аргументов и пробрасывает код возврата контейнера:

```bash
tools/struct-linter/lint.sh validate --template go-standard
```

Локальная сборка бинаря:

```bash
go build -o struct-linter ./cmd/struct-linter
./struct-linter validate --template go-standard --project .
```

## Команды

| Команда | Назначение |
|---------|------------|
| `validate` | Проверить структуру проекта по эталону и напечатать вердикт |
| `list-templates` | Перечислить доступные эталоны с идентификатором, версией и языком |
| `schema` | Выдать замкнутую схему контракта (`input`, `template`, `verdict`) |
| `version` | Напечатать версию сборки линтера |

Ключи команды `validate`:

- `--project` — путь к корню проверяемого проекта (по умолчанию `.`);
- `--template` — идентификатор эталона либо `auto` для авто-подбора по маркерам;
- `--template-version` — версия эталона (по умолчанию — последняя доступная);
- `--format` — формат вывода: `json` (по умолчанию) или `text`.

Минимальный вызов для слабой модели — путь и авто-подбор эталона:

```bash
struct-linter validate --template auto --project /work
```

Перечень эталонов, чтобы не угадывать идентификатор:

```bash
struct-linter list-templates
```

## Коды возврата

Исход различается и кодом возврата, и полем `status` вердикта — вызывающая сторона читает любой
из двух каналов.

| Код | `status` | Значение |
|-----|----------|----------|
| `0` | `ok` | Нарушений нет |
| `1` | `violations` | Найдено хотя бы одно нарушение |
| `2` | `error` | Ошибка вызова: эталон не найден, путь недоступен, шаблон не прошёл схему |

## Формат вердикта

Вердикт валиден по схеме [`schemas/verdict.schema.json`](./schemas/verdict.schema.json). Список
нарушений присутствует всегда (пустой при статусе `ok`); каждое нарушение указывает класс, путь,
правило и причину.

```json
{
  "schema_version": "1.0.0",
  "status": "violations",
  "template": { "id": "go-standard", "version": "1.0.0", "language": "go" },
  "violations": [
    {
      "code": "MISSING_REQUIRED",
      "path": "cmd",
      "rule": "cmd-dir",
      "reason": "точки входа приложения размещаются в каталоге cmd"
    }
  ]
}
```

При ошибке вызова вместо нарушений заполняется поле `error`:

```json
{
  "schema_version": "1.0.0",
  "status": "error",
  "violations": [],
  "error": { "code": "template_not_found", "message": "template not found: ..." }
}
```

## Формат эталона

Эталон — файл `templates/<id>/<version>/template.yaml`, валидный по схеме
[`schemas/template.schema.json`](./schemas/template.schema.json). Пример —
[`templates/go-standard/1.0.0/template.yaml`](./templates/go-standard/1.0.0/template.yaml).

Обязательные поля: `schema_version`, `id`, `version`, `language`. Правила задаются секциями
`required`, `forbidden`, `naming`, `layers`; маркеры авто-подбора — секцией `detect`.

```yaml
schema_version: "1.0.0"
id: go-standard
version: "1.0.0"
language: go
detect:
  - go.mod
required:
  - name: cmd-dir
    kind: dir           # file или dir
    match: exact        # exact, glob или regex
    pattern: cmd
    reason: точки входа размещаются в каталоге cmd
```

Поле или значение вне схемы блокирует загрузку эталона с указанием поля, а не игнорируется молча.

## Классы нарушений

| Код | Когда возникает |
|-----|-----------------|
| `MISSING_REQUIRED` | Обязательный путь отсутствует либо glob не набрал минимума совпадений |
| `FORBIDDEN_PRESENT` | В структуре присутствует запрещённый эталоном путь |
| `NAMING_VIOLATION` | Имя в области правила не соответствует его регулярному выражению |
| `LAYER_PATH_VIOLATION` | Путь нарушает объявленную для слоя разметку |

## Разработка

```bash
go test ./...            # тесты
go test -race ./...      # тесты с детектором гонок
gofmt -l .               # проверка форматирования (пусто — норма)
go vet ./...             # статический анализ
golangci-lint run ./...  # набор линтеров (конфигурация .golangci.yml)
```

Структура кода следует Clean Architecture:

- `internal/structlint/domain` — типы эталона, снимок дерева, вердикт, контракты и sentinel-ошибки;
- `internal/structlint/application` — чистое ядро проверки и сценарий валидации;
- `internal/structlint/infrastructure` — обход ФС, репозиторий эталонов, страж схемы, CLI, JSON;
- `cmd/struct-linter` — единственный composition root, где собирается граф зависимостей.

## Ограничения

- В версию v1 входит только валидация структуры (пути, файлы, имена, разметка слоёв путями).
  Анализ графа импортов, стилевой линт и генерация скелета — вне скоупа.
- Разметка слоёв проверяется по путям, а не по реальным зависимостям импортов.
- Линтер читает только имена и пути; содержимое файлов проекта не читается, монтирование — `:ro`.
