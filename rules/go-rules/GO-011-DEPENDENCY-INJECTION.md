## Таблица правил
| ID | Правило |
|----|---------|
| DI-001 | Передавать зависимости через параметры конструктора. |
| DI-002 | Не использовать глобальные service-переменные. |
| DI-003 | Не выполнять service setup в `init()` — только явные конструкторы. |
| DI-004 | Принимать в конструкторах интерфейсы, а не конкретные типы. |
| DI-005 | Размещать DI-container только в composition root (`main()`/старт приложения). |
| DI-006 | Не передавать container как аргумент (антипаттерн service locator). |
| DI-007 | Держать граф зависимостей плоским — не глубже 3 уровней. |
| DI-008 | Управлять жизненным циклом: singleton для stateful, transient для stateless. |
| DI-009 | Обеспечивать health checks и graceful shutdown для сервисов. |
| DI-010 | Выбирать способ по числу сервисов: ручной DI до ~10, дальше — `wire`/`dig`+`fx`. |

## Принцип
Внедрение зависимостей делает зависимости явными и заменяемыми. Конструктор, принимающий интерфейсы, легко тестируется моками; глобальные переменные и `init()`, наоборот, прячут зависимости и делают порядок инициализации непредсказуемым. Сборку графа («wiring») концентрируют в одной точке — composition root (`main`), — а не размазывают по коду и не таскают container повсюду. Плоский граф зависимостей — признак здорового дизайна.

| Понятие | Описание |
|---------|----------|
| `Constructor injection` | Передача зависимостей через параметры конструктора. |
| `Composition root` | Единственное место сборки графа зависимостей (обычно `main`). |
| `Service locator` | Антипаттерн: передача container как зависимости для «доставания» сервисов. |

## Подробное описание

**[DI-001]** Зависимости передавайте параметрами конструктора (`NewUserService(db, mailer, logger)`). Так они видимы, обязательны и подменяемы.

**[DI-002]** Глобальные service-переменные (`var db *sql.DB`) — скрытая зависимость, которую нельзя замокать. Заменяйте на поля структуры, заполняемые конструктором.

**[DI-003]** Не настраивайте сервисы в `init()`: скрытые зависимости, непредсказуемый порядок, невозможность вернуть ошибку. Используйте явный конструктор.

**[DI-004]** Конструкторы принимают интерфейсы (`db UserStore`), а не конкретные типы (`db *sql.DB`). Это позволяет подменять реализацию и следует SOLID.

**[DI-005]** DI-container создавайте и настраивайте только в composition root — `main()` или старт приложения. Один container на приложение, а не на запрос.

**[DI-006]** Не передавайте container внутрь сервисов как аргумент: это service locator, который прячет реальные зависимости и создаёт tight coupling.

**[DI-007]** Держите граф плоским. Глубокие цепочки A→B→C→D→E сигнализируют о проблемах дизайна; ориентир — не более 3 уровней вложенности.

**[DI-008]** Осознанно выбирайте lifecycle: stateful-ресурсы (БД, кэш, пул) — singleton; stateless-обработчики — transient.

**[DI-009]** Сервисы с ресурсами должны поддерживать health checks и graceful shutdown, чтобы корректно освобождать соединения при остановке.

**[DI-010]** До ~10 сервисов достаточно ручного DI (без внешних зависимостей). При росте и потребности в lifecycle-менеджменте применяйте `google/wire` (compile-time, кодогенерация) или `uber-go/dig`+`fx` (reflection, управление жизненным циклом).

> **Важно:** передача container как параметра (нарушение DI-006) внешне похожа на DI, но это service locator — он снова прячет зависимости, ради устранения которых DI и вводится.

## Пример

```go
// [DI-001][DI-004] явные зависимости-интерфейсы через конструктор
type UserService struct {
    db     UserStore
    mailer Mailer
    logger *slog.Logger
}

func NewUserService(db UserStore, mailer Mailer, logger *slog.Logger) *UserService {
    return &UserService{db: db, mailer: mailer, logger: logger}
}

// [DI-005] wiring только в composition root
func main() {
    logger := slog.Default()
    db := postgres.NewUserStore(connStr)
    mailer := smtp.NewMailer(smtpAddr)
    userSvc := NewUserService(db, mailer, logger)
    api := NewAPI(userSvc, logger)
    _ = api.ListenAndServe(":8080")
}
```

```go
// ❌ Нарушение [DI-002][DI-003] — глобал + init()
var db *sql.DB
func init() {
    var err error
    db, err = sql.Open("postgres", os.Getenv("DATABASE_URL"))
    if err != nil {
        log.Fatal(err)
    }
}

// ✅ Правильно — зависимость-интерфейс в конструкторе
type UserService struct {
    db UserStore
}

func NewUserService(db UserStore) *UserService {
    return &UserService{db: db}
}
```

Ориентир по выбору подхода:

| Подход | Когда использовать |
|--------|--------------------|
| Ручной DI | < 10 сервисов, простое wiring |
| `google/wire` | 10–15 сервисов, compile-time проверка графа |
| `uber-go/dig` + `fx` | > 15 сервисов, lifecycle management |

## Исключения и граничные случаи
| Ситуация | Как поступить |
|----------|---------------|
| Регистрация driver'а в `init()` | Допустима (это не setup сервиса), но соединение открывать в конструкторе (DI-003). |
| Кросс-зависимости при 15+ сервисах | Ручной DI ломается — переходить на DI-библиотеку (DI-010). |
| Опциональная зависимость | Использовать functional options поверх конструктора, но не глобал (DI-001/DI-002). |
