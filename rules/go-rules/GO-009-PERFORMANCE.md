## Таблица правил
| ID | Правило |
|----|---------|
| PERF-001 | Профилировать `pprof` до оптимизации — не полагаться на интуицию. |
| PERF-002 | Приоритет — снижение аллокаций (часто больший ROI, чем CPU); анализировать через `pprof -alloc_objects`. |
| PERF-003 | Сравнивать before/after статистически через `benchstat` (10+ прогонов). |
| PERF-004 | Проверять внешние узкие места (DB, сеть, API) прежде микрооптимизаций. |
| PERF-005 | Использовать `sync.Pool` для частых аллокаций (буферы, объекты). |
| PERF-006 | Настраивать GC: задавать `GOMEMLIMIT` в контейнерах, `GOGC` для поведения GC. |
| PERF-007 | Оптимизировать memory layout под кэш (struct-of-arrays на горячих путях). |
| PERF-008 | Не логировать в hot loops — это аллоцирует и мешает inlining. |
| PERF-009 | Не использовать `reflect.DeepEqual` на горячих путях — типизированное сравнение в 50–200× быстрее. |
| PERF-010 | Не применять `panic`/`recover` как control flow — аллоцирует stack trace. |
| PERF-011 | Не применять `unsafe` без benchmark-доказательства выигрыша (>10%). |
| PERF-012 | Для HTTP-клиента задавать кастомный `Transport` с пулом соединений. |
| PERF-013 | Документировать оптимизации комментариями с числами из бенчмарков. |

## Принцип
Оптимизация без измерения — потерянное время: интуиция ошибается примерно в 80% случаев. Поэтому дисциплина одна: сначала профилирование (`pprof`), затем целевое исправление конкретного узкого места, затем статистическая проверка (`benchstat`). Чаще всего наибольший выигрыш даёт снижение аллокаций, а не микрооптимизация CPU. И прежде чем трогать код, стоит убедиться, что узкое место вообще внутри процесса, а не в БД или сети.

| Понятие | Описание |
|---------|----------|
| `Hot-path` | Часто исполняемый критический участок, где оптимизация окупается. |
| `Allocation` | Выделение памяти в куче; создаёт давление на GC. |
| `pprof` / `benchstat` | Инструменты профилирования и статистического сравнения бенчмарков. |

## Подробное описание

**[PERF-001]** Всегда профилируйте `pprof` (CPU и heap) до оптимизации. Оптимизация «по наитию» в большинстве случаев бьёт мимо реального узкого места.

**[PERF-002]** Начинайте со снижения аллокаций — это обычно больший ROI, чем экономия тактов CPU. Ищите их через `pprof -alloc_objects`.

**[PERF-003]** Сравнивайте до/после статистически: `go test -bench=. -count=10` и `benchstat`. Единичный замер обманчив.

**[PERF-004]** Проверьте внешние узкие места: если 90% latency в SQL-запросе, оптимизируйте запрос (индекс, prepared statement, батчинг), а не Go-код вокруг.

**[PERF-005]** Для часто создаваемых объектов (буферы, соединения) используйте `sync.Pool`, чтобы переиспользовать память вместо новых аллокаций.

**[PERF-006]** Настраивайте GC под окружение: `GOMEMLIMIT` в контейнерах (иначе OOM-kill и GC-thrashing), `GOGC` — для тонкой настройки частоты сборок.

**[PERF-007]** На горячих путях учитывайте cache locality: struct-of-arrays вместо array-of-structs даёт последовательный доступ к памяти.

**[PERF-008]** Не логируйте внутри hot loop: вызов логгера аллоцирует (даже при выключенном уровне) и мешает inlining — замедление на порядки.

**[PERF-009]** `reflect.DeepEqual` в 50–200× медленнее типизированного сравнения. На горячих путях сравнивайте поля напрямую.

**[PERF-010]** Не используйте `panic`/`recover` как поток управления: `panic` аллоцирует stack trace. Для ожидаемых ошибок — обычный возврат `error`.

**[PERF-011]** `unsafe` оправдан только при доказанном бенчмарком выигрыше (>10%). Иначе это сложность без выгоды.

**[PERF-012]** Дефолтный `http.Client` имеет `MaxIdleConnsPerHost = 2` — под нагрузкой это connection starvation. Задавайте кастомный `Transport` с адекватным пулом.

**[PERF-013]** Документируйте применённые оптимизации комментариями с конкретными числами (`// -26.5%, benchstat p=0.000`), чтобы решения были воспроизводимы.

> **Важно:** Профилирование — не опция, а первый шаг (PERF-001). Любая оптимизация без `pprof`-данных и `benchstat`-подтверждения считается недоказанной.

## Пример

```go
// [PERF-005] пулинг буферов через sync.Pool
var bufPool = sync.Pool{
    New: func() any { return bytes.NewBuffer(make([]byte, 0, 1024)) },
}

func Process(data []byte) []byte {
    buf := bufPool.Get().(*bytes.Buffer)
    defer bufPool.Put(buf)
    buf.Reset()
    // ... работа с buf ...
    return buf.Bytes()
}
```

```go
// ❌ Нарушение [PERF-012] — дефолтный клиент, MaxIdleConnsPerHost=2
var client = &http.Client{}

// ✅ Правильно — кастомный Transport с пулом
var client = &http.Client{
    Transport: &http.Transport{
        MaxIdleConns:        100,
        MaxIdleConnsPerHost: 10,
    },
}
```

```text
# [PERF-003] статистическое сравнение
$ go test -bench=. -count=10 > before.txt
$ # изменения...
$ go test -bench=. -count=10 > after.txt
$ benchstat before.txt after.txt
name          old time/op   new time/op   delta
ProcessUsers  10.2µs ± 3%   7.5µs ± 2%   -26.5%  (p=0.000 n=9+10)
```

## Исключения и граничные случаи
| Ситуация | Как поступить |
|----------|---------------|
| Код не на горячем пути | Не усложнять преждевременно; читаемость важнее (PERF-001). |
| `sync.Pool` для долгоживущих объектов | Не применять — Pool рассчитан на короткоживущие временные объекты (PERF-005). |
| Узкое место во внешней системе | Оптимизировать её (индекс/кэш/батч), а не Go-обвязку (PERF-004). |
