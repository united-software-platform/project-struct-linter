## Таблица правил
| ID | Правило |
|----|---------|
| TEST-001 | Использовать `require` для предусловий (setup, проверка ошибок), прерывающих тест. |
| TEST-002 | Использовать `assert` для верификаций, не прерывающих тест. |
| TEST-003 | Соблюдать порядок аргументов: ожидаемое, затем фактическое. |
| TEST-004 | Вызывать `mock.AssertExpectations(t)` после настройки mock. |
| TEST-005 | Сравнивать ошибки через `errors.Is`/`ErrorIs`, а не по значению — из-за wrapping. |
| TEST-006 | Запускать test suite через `suite.Run(t, new(...))`. |
| TEST-007 | Для сравнения по значению (не по адресу) использовать `EqualExportedValues`/`EqualValues`. |
| TEST-008 | Применять специализированные assertions: `ElementsMatch`, `JSONEq`, `InDelta`, `WithinDuration`, `Eventually`. |

## Принцип
testify разделяет два намерения: `require` останавливает тест немедленно (для предусловий, без которых дальнейшие проверки бессмысленны), `assert` фиксирует провал и продолжает (для независимых верификаций). Путаница между ними приводит либо к каскаду ложных ошибок, либо к падению теста на несущественной проверке. Отдельный источник багов — забытый `AssertExpectations`, из-за которого mock-ожидания «проходят» молча, и сравнение обёрнутых ошибок по значению.

| Понятие | Описание |
|---------|----------|
| `assert` | Записывает провал и продолжает выполнение теста. |
| `require` | Вызывает `t.FailNow()` — немедленно прерывает тест. |
| `AssertExpectations` | Проверка, что все настроенные вызовы mock действительно произошли. |

## Подробное описание

**[TEST-001]** `require` — для предусловий: setup, проверка что ошибки нет перед использованием результата. Если предусловие не выполнено, продолжать тест нет смысла — `require` прерывает его. Для читаемости алиас `must`.

**[TEST-002]** `assert` — для независимых верификаций в конце теста: он записывает провал и продолжает, позволяя увидеть сразу все несоответствия. Алиас `is`.

**[TEST-003]** Соблюдайте порядок аргументов testify: сначала ожидаемое (expected), затем фактическое (actual). Перепутанный порядок делает сообщения об ошибке вводящими в заблуждение.

**[TEST-004]** После настройки mock обязательно вызывайте `mock.AssertExpectations(t)` — иначе незакрытые ожидания проходят молча и тест не ловит отсутствие вызова.

**[TEST-005]** Ошибки сравнивайте через `errors.Is`/`assert.ErrorIs`, а не `assert.Equal(ErrX, err)`: обёрнутая ошибка не равна исходной по значению.

**[TEST-006]** Test suite запускайте через `suite.Run(t, new(MySuite))`. Без лаунчера методы suite не выполняются, и тест «проходит» с нулём проверок.

**[TEST-007]** Для сравнения значений, а не указателей, используйте `EqualExportedValues`/`EqualValues` — `Equal` на указателях сравнивает адреса.

**[TEST-008]** Применяйте подходящие assertions: `ElementsMatch` (без учёта порядка), `JSONEq` (игнор пробелов/порядка ключей), `InDelta` (допуск для float), `WithinDuration` (время), `Regexp`, `Eventually`/`EventuallyWithT` (асинхронное ожидание).

> **Важно:** отсутствие `suite.Run()` (нарушение TEST-006) — коварный баг: тесты suite не запускаются, а `go test` показывает успех с нулевым числом проверок.

## Пример

```go
func TestGetUser(t *testing.T) {
    store := new(MockStore)
    store.On("GetUser", mock.Anything, "42").Return(&User{ID: "42"}, nil)

    svc := NewService(store)

    user, err := svc.GetUser(context.Background(), "42")
    require.NoError(t, err)          // [TEST-001] предусловие
    assert.Equal(t, "42", user.ID)   // [TEST-002][TEST-003] expected, actual

    store.AssertExpectations(t)       // [TEST-004]
}
```

```go
// ❌ Нарушение [TEST-005] — сравнение обёрнутой ошибки по значению
assert.Equal(t, ErrNotFound, err)

// ✅ Правильно — errors.Is через ErrorIs
assert.ErrorIs(t, err, ErrNotFound)
```

Выбор между assert и require:

| Использовать | Когда |
|--------------|-------|
| `require` | Предусловия, setup, проверки ошибок перед использованием результата |
| `assert` | Независимые верификации в конце теста |

## Исключения и граничные случаи
| Ситуация | Как поступить |
|----------|---------------|
| Несколько независимых проверок результата | `assert`, чтобы увидеть все провалы сразу, а не первый (TEST-002). |
| Сравнение неупорядоченных коллекций | `ElementsMatch` вместо `Equal` (TEST-008). |
| Асинхронный результат (eventual consistency) | `Eventually`/`EventuallyWithT` вместо `time.Sleep` (TEST-008). |
