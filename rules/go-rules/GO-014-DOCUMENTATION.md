## Таблица правил
| ID | Правило |
|----|---------|
| DOC-001 | Каждый пакет снабжать package comment. |
| DOC-002 | Все exported функции и типы снабжать doc comment. |
| DOC-003 | Doc comment начинать с имени сущности и глагольной фразы. |

| DOC-009 | Синхронизировать документацию с кодом при изменении public API. |

## Принцип
Документация — часть API, а не приложение к нему. Хороший doc comment объясняет назначение и условия применения (why/when), а не пересказывает сигнатуру (what). Package comment даёт цель пакета без чтения кода, README удерживает пользователя структурой и быстрым стартом, а исполняемые `ExampleXxx` одновременно документируют и тестируют использование. Фокус на «зачем» отличает полезную документацию от шумной.

| Понятие | Описание |
|---------|----------|
| `Doc comment` | Комментарий перед exported сущностью, начинающийся с её имени. |
| `Package comment` | Комментарий, описывающий назначение пакета, перед `package`. |
| `ExampleXxx` | Тестируемый пример из пакета `_test`, проверяемый по `// Output:`. |

## Подробное описание

**[DOC-001]** Каждый пакет должен иметь package comment (перед `package name`), объясняющий его назначение. Без него цель пакета приходится реконструировать из кода.

**[DOC-002]** Все exported функции, типы, константы и переменные снабжайте doc comment. Публичное API без описания увеличивает стоимость сопровождения.

**[DOC-003]** Начинайте doc comment с имени сущности и глагольной фразы: `// CalculateDiscount вычисляет...`. Так godoc и IDE формируют корректные подсказки.

**[DOC-004]** Описывайте назначение и условия применения, а не механику. `// Функция принимает a, b и возвращает c` бесполезно; ценно — когда и зачем вызывать, что возвращается в ошибках.

**[DOC-005]** README оформляйте по устоявшейся структуре: бейджи, обзор, установка и базовое использование (Getting Started), возможности, примеры. Плохо структурированный README теряет пользователей.

**[DOC-006]** CONTRIBUTING должен давать рабочий старт менее чем за 10 минут: клонирование, тесты, линтер, как открыть PR. Долгая настройка убивает вовлечённость.

**[DOC-007]** Ведите CHANGELOG в формате Keep a Changelog с секциями Added/Changed/Breaking и версиями по SemVer — иначе обновление зависимостей становится рискованным.

**[DOC-008]** Для библиотек пишите `ExampleXxx`-функции с блоком `// Output:` — они исполняются `go test`, гарантируя, что примеры не устаревают.

**[DOC-009]** При изменении public API обновляйте документацию в том же изменении. Рассинхрон документации и кода хуже её отсутствия.

> **Важно:** doc comment, начинающийся с «Функция...» вместо имени сущности (нарушение DOC-003), ломает извлечение документации инструментами godoc.

## Пример

```go
// Package calculator предоставляет расчёт цены с прогрессивными скидками.
//
// Скидки применяются прогрессивно: каждый уровень добавляет процент.
// Используйте CalculateDiscount для вычисления итоговой цены.
package calculator

// CalculateDiscount вычисляет итоговую цену после применения скидок по уровням.
//
// Скидки применяются прогрессивно в зависимости от количества заказа.
// Возвращает ErrInvalidPrice, если basePrice отрицательный, и
// ErrInvalidQuantity, если quantity не положительный.
func CalculateDiscount(basePrice float64, quantity int, tiers []DiscountTier) (float64, error) {
    // ...
}
```

```go
// ❌ Нарушение [DOC-003][DOC-004] — не с имени, описывает what
// Функция CalculateDiscount принимает basePrice, quantity и tiers.
func CalculateDiscount(...) (float64, error) { /* ... */ }

// ✅ Правильно — имя + назначение
// CalculateDiscount вычисляет итоговую цену после применения скидок по уровням.
func CalculateDiscount(...) (float64, error) { /* ... */ }
```

```go
// [DOC-008] исполняемый пример
func ExampleCalculateDiscount() {
    price, _ := calculator.CalculateDiscount(100.00, 75, tiers)
    fmt.Printf("Final price: $%.2f\n", price)
    // Output: Final price: $78.75
}
```

## Исключения и граничные случаи
| Ситуация | Как поступить |
|----------|---------------|
| Приложение/CLI без публичного API | Фокус на README (установка, конфиг, help), `ExampleXxx` не обязательны (DOC-008). |
| Тривиальный самоочевидный геттер | Короткий doc comment всё равно нужен для exported (DOC-002), но без избыточности. |
| Внутренний пакет `internal/` | Package comment полезен, но требования к README/CHANGELOG не применяются (DOC-005). |
