## Таблица правил
| ID | Правило |
|----|---------|
| STRUCT-001 | Держать интерфейсы маленькими (1–3 метода), крупные — компоновать из мелких. |
| STRUCT-002 | Определять интерфейс на стороне потребителя, а не реализатора. |
| STRUCT-003 | Принимать интерфейсы, возвращать конкретные структуры. |
| STRUCT-004 | Не создавать интерфейс преждевременно — дождаться 2+ реализаций. |
| STRUCT-005 | Проектировать полезное zero value, чтобы тип был готов к использованию без конструктора. |
| STRUCT-006 | Делать type assertion только через comma-ok (`v, ok := x.(T)`). |
| STRUCT-007 | Использовать type switch для динамического определения типа. |
| STRUCT-008 | Embedding — для полного продвижения API; именованное поле — для внутреннего использования. |
| STRUCT-009 | Pointer receiver — для мутации/больших структур/мьютексов; value receiver — для мелких неизменяемых типов. |
| STRUCT-010 | Использовать единый тип receiver (pointer или value) для всех методов типа. |
| STRUCT-011 | Проверять реализацию интерфейса на этапе компиляции: `var _ Iface = (*Type)(nil)`. |
| STRUCT-012 | Добавлять теги сериализации у struct, которые маршалятся/анмаршалятся. |
| STRUCT-013 | Реализовывать `String() string` (Stringer), а не `ToString()`. |
| STRUCT-014 | Защищать некопируемые структуры sentinel `noCopy`. |

## Принцип
Сила Go-типов — в композиции и маленьких интерфейсах. Узкий интерфейс, объявленный там, где он потребляется, даёт слабую связанность и лёгкое тестирование. Конструкторы должны возвращать конкретный тип, чтобы не терять информацию, а zero value стоит проектировать полезным, чтобы тип работал без обязательной инициализации. Ранние абстракции с единственной реализацией добавляют косвенность без выгоды.

| Понятие | Описание |
|---------|----------|
| `Embedding` | Встраивание типа в struct/interface с продвижением его методов наружу. |
| `Comma-ok` | Форма `v, ok := x.(T)`, не паникующая при несоответствии типа. |
| `Zero value` | Значение переменной без явной инициализации; должно быть пригодным к использованию. |

## Подробное описание

**[STRUCT-001]** Интерфейс на 5+ методов — слабая абстракция. Держите 1–3 метода, крупный контракт собирайте композицией мелких (как `io.ReadWriteCloser`).

**[STRUCT-002]** Контракт должен контролировать потребитель. Объявляйте интерфейс в пакете, который его использует, а не в пакете реализации — это разрывает лишние зависимости.

**[STRUCT-003]** Принимайте интерфейсы (гибкость входа), возвращайте конкретные структуры (полнота информации у вызывающего). Возврат интерфейса из конструктора скрывает доступные методы.

**[STRUCT-004]** Не вводите интерфейс, пока нет 2+ реальных реализаций (или явной нужды в тестовом моке). Преждевременная абстракция — лишняя косвенность.

**[STRUCT-005]** Проектируйте zero value полезным: `var mu sync.Mutex`, `var buf bytes.Buffer` работают сразу. Если тип требует инициализации (nil map/slice внутри) — обязателен конструктор.

**[STRUCT-006]** Прямое `v := x.(T)` паникует при несоответствии. Всегда используйте comma-ok: `v, ok := x.(T)`.

**[STRUCT-007]** Для ветвления по динамическому типу применяйте type switch (`switch t := x.(type)`), а не цепочку assertion'ов.

**[STRUCT-008]** Embedding продвигает весь API встроенного типа наружу — используйте, когда именно это нужно (`Server` расширяет `http.Handler`). Если нужны лишь несколько методов внутри — используйте именованное поле (`Server` имеет `store`).

**[STRUCT-009]** Pointer receiver — для мутации, больших структур и типов с мьютексом. Value receiver — для маленьких неизменяемых типов.

**[STRUCT-010]** Не смешивайте pointer и value receiver у одного типа — это порождает неочевидное поведение и мешает удовлетворению интерфейсов. Выберите один и применяйте ко всем методам.

**[STRUCT-011]** Фиксируйте соответствие интерфейсу на этапе компиляции: `var _ io.Reader = (*MyReader)(nil)`. Ошибка обнаружится при сборке, а не в рантайме.

**[STRUCT-012]** У сериализуемых структур задавайте теги (`json:"..."`, `db:"..."`), иначе анмаршалинг даёт неожиданные результаты при изменении имён.

**[STRUCT-013]** Для строкового представления реализуйте `String() string` — это интерфейс `fmt.Stringer`, который понимают `fmt` и логгеры. `ToString()` они не знают.

**[STRUCT-014]** Структуры, которые нельзя копировать (содержат мьютекс/счётчик), защищайте sentinel-полем `noCopy`, чтобы `go vet` ловил копирование.

> **Важно:** Смешивание value и pointer receiver (STRUCT-010) приводит к тому, что интерфейс удовлетворяется только указателем — типичный источник ошибок «does not implement».

## Пример

```go
// [STRUCT-001] маленький интерфейс, объявлен у потребителя [STRUCT-002]
type Store interface {
    Get(ctx context.Context, id string) (User, error)
}

// [STRUCT-003] конструктор возвращает конкретный тип
func NewService(s Store) *Service { return &Service{store: s} }

// [STRUCT-011] проверка реализации на этапе компиляции
var _ io.Reader = (*MyReader)(nil)

// [STRUCT-006] безопасный type assertion
if v, ok := x.(string); ok {
    use(v)
}
```

```go
// ❌ Нарушение [STRUCT-006] — паника при несоответствии типа
name := payload.(string)

// ✅ Правильно
name, ok := payload.(string)
if !ok {
    return fmt.Errorf("payload: ожидалась строка")
}
```

Ключевые интерфейсы стандартной библиотеки для ориентира:

| Интерфейс | Пакет | Метод |
|-----------|-------|-------|
| `Reader` | io | `Read(p []byte) (n int, err error)` |
| `Writer` | io | `Write(p []byte) (n int, err error)` |
| `Closer` | io | `Close() error` |
| `Stringer` | fmt | `String() string` |
| `error` | builtin | `Error() string` |
| `Handler` | net/http | `ServeHTTP(ResponseWriter, *Request)` |

## Исключения и граничные случаи
| Ситуация | Как поступить |
|----------|---------------|
| Единственная реализация, но нужен мок в тестах | Допустимо ввести интерфейс ради тестируемости (исключение из STRUCT-004). |
| Тип содержит nil map/slice | Полезное zero value недостижимо — предоставьте конструктор (STRUCT-005). |
| Крупный сторонний интерфейс | Оборачивайте адаптером с узким интерфейсом на стороне потребителя (STRUCT-001/002). |
