## Таблица правил
| ID | Правило |
|----|---------|
| ERR-001 | Никогда не игнорировать ошибку через `_` — всегда проверять. |
| ERR-002 | Оборачивать ошибку с контекстом через `fmt.Errorf("...: %w", err)`, не через `%v`. |
| ERR-003 | Строки ошибок писать строчными буквами и без завершающей пунктуации. |
| ERR-004 | Инспектировать ошибки через `errors.Is`/`errors.As`, а не через `==`/`!=`. |
| ERR-005 | Обрабатывать ошибку один раз: либо залогировать, либо вернуть — не оба. |
| ERR-006 | Переводить инфраструктурные ошибки в доменные sentinel-ошибки на границе слоя. |
| ERR-007 | Не использовать `panic` для ожидаемых ошибок. |
| ERR-008 | Логировать структурированно через проектный `lgr`, а не `fmt.Println`/`log.Printf`. |
| ERR-009 | Переменные данные помещать в атрибуты лога, а не в строку сообщения ошибки (low cardinality). |
| ERR-010 | Логировать ошибку один раз на верхнем уровне (HTTP/gRPC middleware, main). |
| ERR-011 | Объединять независимые ошибки через `errors.Join` (Go 1.20+). |

## Принцип
Ошибка в Go — это значение, а не исключение. Полезность обработки определяется тремя вещами: сохранением цепочки контекста (`%w`), возможностью инспекции (`errors.Is`/`errors.As`) и однократной обработкой. Нарушение «single handling» — логирование и возврат одной и той же ошибки — приводит к дублям в агрегаторах и усложняет отладку. Переменные данные должны жить в атрибутах структурированного лога, а не в тексте сообщения, иначе ломается группировка по кардинальности.

| Понятие | Описание |
|---------|----------|
| `Error wrapping` | Добавление контекста с сохранением исходной ошибки через `%w`. |
| `Sentinel error` | Заранее объявленная доменная ошибка (`ErrUserNotFound`) для сравнения. |
| `Single handling` | Ошибка обрабатывается ровно один раз: либо возвращается, либо логируется. |

## Подробное описание

**[ERR-001]** Никогда не отбрасывайте ошибку через `_`. Молчаливый сбой невозможно диагностировать. Каждая возвращённая ошибка должна быть проверена.

**[ERR-002]** Оборачивайте ошибку с контекстом операции через `%w`: `fmt.Errorf("querying user %s: %w", id, err)`. `%v` рвёт цепочку и ломает `errors.Is/As`.

**[ERR-003]** Строки ошибок — строчными, без точки в конце: они конкатенируются в цепочки (`errors.New("not found")`).

**[ERR-004]** Проверяйте ошибки через `errors.Is` (значение) и `errors.As` (тип). `==` не работает с обёрнутыми ошибками.

**[ERR-005]** Соблюдайте single handling: либо возвращаете ошибку с контекстом наверх, либо логируете — но не то и другое сразу. Иначе одна ошибка попадёт в логи многократно.

**[ERR-006]** На границе слоя переводите инфраструктурные ошибки в доменные: `sql.ErrNoRows` → `ErrUserNotFound`. Верхние слои не должны знать про SQL.

**[ERR-007]** `panic` — для действительно неустранимых состояний (нарушение инварианта программы), а не для ожидаемых ошибок вроде «пользователь не найден».

**[ERR-008]** Логируйте структурированно через проектный логгер `lgr` (`lg.Info`, `lg.Warning`, `lg.Error`, `lg.AddInfo`). `fmt.Println`/`log.Printf` не структурированы и плохо фильтруются.

**[ERR-009]** Переменные данные (id, значения) кладите в атрибуты (`lg.AddInfo("userId", id)`), а не в текст ошибки. Это сохраняет low cardinality и позволяет фильтровать по атрибуту.

**[ERR-010]** Единственная точка логирования — верхний уровень (HTTP/gRPC middleware, `main`). Нижние слои только возвращают ошибку с контекстом.

**[ERR-011]** Несколько независимых ошибок (например, из параллельных операций) объединяйте через `errors.Join`, а не через ручную конкатенацию строк.

> **Важно:** Нарушение [ERR-005] («log and return») — самая частая причина дублей в логах: ошибка логируется в сервисе, затем в middleware, затем в `main`.

## Пример

```go
var ErrUserNotFound = errors.New("user not found")

// [ERR-006] перевод в доменную ошибку, [ERR-002] оборачивание с контекстом
func (s *PostgresUserStore) GetUser(ctx context.Context, id string) (*User, error) {
    var u User
    err := s.db.QueryRowContext(ctx, "SELECT id, name FROM users WHERE id=$1", id).
        Scan(&u.ID, &u.Name)
    if err != nil {
        if errors.Is(err, sql.ErrNoRows) {   // [ERR-004]
            return nil, ErrUserNotFound
        }
        return nil, fmt.Errorf("querying user %s: %w", id, err)
    }
    return &u, nil
}
```

```go
// ❌ Нарушение [ERR-005] — ошибка и логируется, и возвращается
func (s *UserService) ProcessUser(ctx context.Context, id string) error {
    user, err := s.store.GetUser(ctx, id)
    if err != nil {
        lg.Error("ProcessUser.error", err.Error())
        return fmt.Errorf("getting user %s: %w", id, err)
    }
    _ = user
    return nil
}

// ✅ Правильно — возврат с контекстом, лог один раз наверху [ERR-010]
func (s *UserService) ProcessUser(ctx context.Context, id string) error {
    user, err := s.store.GetUser(ctx, id)
    if err != nil {
        return fmt.Errorf("getting user %s: %w", id, err)
    }
    _ = user
    return nil
}
```

```go
// ❌ Нарушение [ERR-009] — переменные данные в строке ошибки
return fmt.Errorf("failed to process user %s with data %v", id, variableData)

// ✅ Правильно — переменные данные в атрибутах
lg.AddInfo("userId", id)
lg.AddInfo("data", variableData)
lg.Error("ProcessUser.error", "failed to process user")
```

## Исключения и граничные случаи
| Ситуация | Как поступить |
|----------|---------------|
| Ошибка действительно нерелевантна (например, `Close()` в defer при чтении) | Явно игнорировать через `_ = f.Close()` с комментарием, а не молча (ERR-001). |
| Нарушен инвариант программы (недостижимое состояние) | Допустим `panic` — это не ожидаемая ошибка (ERR-007). |
| Параллельные операции с несколькими ошибками | Использовать `errors.Join`, а не первую попавшуюся (ERR-011). |
