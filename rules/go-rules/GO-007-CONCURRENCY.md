## Таблица правил
| ID | Правило |
|----|---------|
| CONC-001 | Каждая горутина должна иметь явный механизм остановки (context, done-канал, WaitGroup). |
| CONC-002 | В `select` долгоживущей горутины слушать `ctx.Done()` для выхода по отмене. |
| CONC-003 | Вызывать `wg.Add()` до запуска `go`, а не внутри горутины. |
| CONC-004 | Закрывать канал должен только отправитель, не получатель. |
| CONC-005 | Указывать направление канала в сигнатурах (`chan<-`, `<-chan`). |
| CONC-006 | Передавать через каналы копии, а не указатели на общее состояние. |
| CONC-007 | Не использовать `time.After` в циклах — применять `time.NewTimer` + `Reset`. |
| CONC-008 | Ограничивать число горутин (worker pool), не спавнить неограниченно. |
| CONC-009 | Не удерживать мьютекс во время I/O. |
| CONC-010 | Использовать `sync.Map` только для read-heavy нагрузок; для write-heavy — `sync.RWMutex`. |
| CONC-011 | Группы горутин с ошибками оформлять через `errgroup`. |
| CONC-012 | Включать `-race` в CI и `goleak` в тестах для поиска гонок и утечек. |

## Принцип
Go поощряет «share memory by communicating»: каналы явно передают владение данными, а мьютексы защищают разделяемое состояние. Главный источник багов — горутины без гарантированного выхода (утечки) и гонки. Поэтому у каждой горутины должен быть механизм остановки, у каждого канала — понятный владелец, закрывающий его, а конкурентный код должен прогоняться под детектором гонок. Таймеры в циклах и удержание блокировок через I/O — типичные источники накопления ресурсов.

| Понятие | Описание |
|---------|----------|
| `Exit mechanism` | Способ гарантированно завершить горутину (context/done-канал/WaitGroup). |
| `Channel ownership` | Правило «закрывает тот, кто отправляет»; получатель только читает. |
| `Goroutine leak` | Горутина, которая никогда не завершается и держит ресурсы. |

## Подробное описание

**[CONC-001]** Fire-and-forget горутины текут. У каждой должен быть явный выход: отмена через `context`, закрытие done-канала или ожидание через `WaitGroup`.

**[CONC-002]** В `select` долгоживущей горутины первым кейсом слушайте `ctx.Done()` и возвращайтесь при отмене (обычно с `return ctx.Err()`).

**[CONC-003]** `wg.Add(n)` вызывайте до `go`, а не внутри горутины: иначе `Wait()` может вернуться до старта горутин (гонка). В Go 1.24+ доступен `wg.Go()`.

**[CONC-004]** Канал закрывает только отправитель. Закрытие получателем приводит к панике, если отправитель ещё пишет.

**[CONC-005]** В сигнатурах указывайте направление канала (`chan<- T` для отправки, `<-chan T` для приёма) — компилятор защитит от неправильного использования.

**[CONC-006]** Через каналы передавайте копии значений. Передача указателей создаёт невидимое общее состояние и обесценивает смысл каналов.

**[CONC-007]** `time.After` в цикле создаёт новый таймер на каждой итерации, живущий до срабатывания — накопление памяти. Используйте один `time.NewTimer` с `Reset`.

**[CONC-008]** Не спавните горутины неограниченно под нагрузкой — используйте worker pool фиксированного размера, иначе исчерпаете ресурсы.

**[CONC-009]** Не держите мьютекс во время I/O (сеть, диск): блокировка удерживается непредсказуемо долго и сериализует систему. Сузьте критическую секцию.

**[CONC-010]** `sync.Map` оптимизирован под read-heavy сценарии. Для write-heavy используйте обычную карту под `sync.RWMutex`.

**[CONC-011]** Для групп горутин, возвращающих ошибки, используйте `errgroup.WithContext`: он собирает первую ошибку и отменяет остальные через общий context.

**[CONC-012]** Включайте `go test -race` в CI и `go.uber.org/goleak` в тестах — гонки и утечки иначе остаются скрытыми до продакшена.

> **Важно:** `wg.Add` внутри горутины (нарушение CONC-003) — классическая гонка: `Wait()` может увидеть счётчик 0 и вернуться раньше, чем горутины стартовали.

## Пример

```go
// [CONC-001][CONC-002] горутина с механизмом остановки
func worker(ctx context.Context, ch <-chan Task) {
    for {
        select {
        case <-ctx.Done():
            return
        case task, ok := <-ch:
            if !ok {
                return
            }
            process(task)
        }
    }
}

// [CONC-003] wg.Add до go
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()
    worker(ctx, ch)
}()
```

```go
// ❌ Нарушение [CONC-007] — новый таймер каждую итерацию
for {
    select {
    case <-time.After(time.Second):
        process()
    }
}

// ✅ Правильно — переиспользуемый таймер
timer := time.NewTimer(time.Second)
defer timer.Stop()
for {
    select {
    case <-timer.C:
        process()
        timer.Reset(time.Second)
    }
}
```

```go
// [CONC-011] группа горутин с errgroup
func processAll(ctx context.Context, items []Item) error {
    g, ctx := errgroup.WithContext(ctx)
    for _, item := range items {
        item := item
        g.Go(func() error {
            return processItem(ctx, item)
        })
    }
    return g.Wait()
}
```

## Исключения и граничные случаи
| Ситуация | Как поступить |
|----------|---------------|
| Единственный отправитель на нескольких получателей | Закрывает всё равно только отправитель (CONC-004). |
| Read-heavy кэш с редкой записью | `sync.Map` уместен; при росте записи переходить на `RWMutex` (CONC-010). |
| Дедупликация одинаковых конкурентных вызовов | Использовать `singleflight` вместо ручной синхронизации. |
