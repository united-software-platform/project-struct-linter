## Context

Мотивация — см. proposal.md (Why). Репозиторий свежий (SDD-kit, без Go-кода), существующие
инструменты — shell/python (`tools/make-lint`, `tools/host-runner`). Действуют правила репо:
Clean Architecture (`CLAR-*`), DDD (`DDD-*`), Docker (`DOCK-*`), Makefile (`MAKE-001`),
документация (`DOC-*`). Концепция требует замкнутых моделей данных (Standard 22) и пригодности
контракта для слабейшей модели.

## Goals / Non-Goals

**Goals:**
- Детерминированное ядро проверки, тестируемое без ФС и контейнера.
- Контракт (вход/шаблон/вердикт) как замкнутые JSON Schema — источник истины границ.
- Простейший вызов для слабой модели: путь + id эталона, JSON-вывод, коды `0/1/2`.
- Эталоны — версионированные данные, отделённые от кода.

**Non-Goals (сверх границ proposal):**
- Никакого DSL-интерпретатора правил: правила — декларативные поля, движок фиксирован.
- Никакого сетевого сервиса в v1: только CLI/контейнер.

## Decisions

### Решение 1: Runtime — Go-бинарь в distroless-образе

Контейнеризация делает язык внутренней деталью, поэтому выбран Go: статический бинарь, быстрый
обход ФС, нативный JSON, встраивание эталонов/схем через `embed`. Альтернативы: Python (тянет
интерпретатор и зависимости в образ — хуже переносимость), shell (JSON-контракт и схемы на shell
хрупки). Образ — distroless/scratch, эталоны и схемы вкомпилированы (самодостаточный след, Standard 20).

### Решение 2: Слои по Clean Architecture, ядро — чистая функция

`domain` — типы и контракты (`Template`, `Rule`, `Violation`, `Verdict`, `TreeSnapshot`,
контракты `TemplateRepository`, `TreeScanner`). `application.ValidateStructure` — чистая логика над
`TreeSnapshot` + `Template`, без ФС и транспорта (`CLAR-010`, тестируема на фикстурах).
`infrastructure` — `fsscanner`, `templaterepo`, `clihandler`, JSON-энкодер, `schemaguard`.
Обработчик CLI зависит от use case, не от домена напрямую (`CLAR-016`). Альтернатива —
монолитный пакет — отвергнута: не изолирует ядро для тестов и нарушает `CLAR-001`.

### Решение 3: Контракт — три замкнутые JSON Schema

`schemas/{input,template,verdict}.schema.json` с `additionalProperties: false`. Шаблон валидируется
по схеме до применения (`schemaguard`) — поле вне схемы блокирует загрузку. Команда `schema`
выдаёт схемы наружу, чтобы вызывающая сторона проверяла свои данные той же схемой. Альтернатива —
валидация «на глаз» в коде — отвергнута: не замкнута и расходится со схемой.

### Решение 4: Вход — обход ФС от пути; discoverability эталонов

Линтер сам обходит смонтированный проект (модель передаёт только `--project` и `--template`).
`list-templates` даёт enum эталонов, `--template auto` подбирает по `detect`-маркерам — снимает с
слабой модели угадывание. Альтернатива — приём снимка дерева в JSON — отвергнута для v1: перекладывает
сбор дерева на слабую модель (риск ошибок). Ядро всё равно работает над снимком, поэтому переход на
приём снимка возможен позже без смены контракта вердикта.

### Решение 5: Коды возврата 0/1/2 + дублирующий `status`

Три исхода различаются и кодом возврата, и полем `status` — слабая модель читает любой из двух
каналов (`SD-FR-005`). Альтернатива — только код возврата — отвергнута: JSON-потребителю удобнее поле.

### Решение 6: Хранение эталонов `templates/<id>/<version>/template.yaml`

Версии раздельными каталогами: один id — много версий, выбор по `--template-version` либо последняя.
Формат YAML (человекочитаемое курирование), валидируется по JSON Schema. Гейт калибровки:
все `templates/**` валидны по схеме, а чистая фикстура даёт вердикт `ok` (аналог «пресет ↔ фикстура»).

## Соответствие правилам Go

Реализация подчиняется своду `rules/go-rules/` (`GO-001`..`GO-017`). Ключевые для этого CLI:

- **Структуры и интерфейсы (`GO-003`)**: контракты `TemplateRepository`, `TreeScanner` — узкие
  (1–3 метода, `STRUCT-001`), объявлены на стороне потребителя-`application` (`STRUCT-002`);
  конструкторы принимают интерфейсы, возвращают конкретные структуры (`STRUCT-003`); соответствие
  интерфейсу фиксируется на компиляции `var _ Iface = (*Type)(nil)` (`STRUCT-011`); интерфейс не
  вводится раньше нужды (`STRUCT-004`, исключение — мок в тестах). Это совместимо с `CLAR-002`
  (контракты репозитория — в домене): домен объявляет, `application` потребляет.
- **Ошибки (`GO-005`)**: обёртка с контекстом через `%w` (`ERR-002`), строки ошибок строчными без
  пунктуации (`ERR-003`), инспекция `errors.Is/As` (`ERR-004`); инфраструктурные ошибки переводятся
  в доменные sentinel на границе слоя (`ERR-006`) — `ErrTemplateNotFound`, `ErrProjectUnreadable`,
  `ErrTemplateInvalid`; обработка однократна, лог — один раз на верхнем уровне (`clihandler`/`main`,
  `ERR-005`/`ERR-010`). Sentinel-ошибки отображаются в код возврата `2` и поле `status: error`.
- **Внедрение зависимостей (`GO-011`)**: constructor injection (`DI-001`), приём интерфейсов
  (`DI-004`), сборка графа только в composition root `cmd/struct-linter/main.go` (`DI-005`); ручной
  DI — сервисов меньше 10 (`DI-010`), без глобалов и `init()` (`DI-002`/`DI-003`).
- **Тестирование (`GO-016`)**: testify — `require` для предусловий (`TEST-001`), `assert` для
  верификаций (`TEST-002`), порядок «ожидаемое, фактическое» (`TEST-003`), сравнение ошибок через
  `ErrorIs` (`TEST-005`), сравнение JSON-вердикта через `JSONEq` и коллекций через `ElementsMatch`
  (`TEST-008`); табличные тесты на фикстурах.
- **Безопасность (`GO-015`)**: линтер не вызывает shell на внешних данных (`SEC-003`) — обёртка
  `lint.sh` собирает `docker run` из явных аргументов; весь внешний ввод (CLI-аргументы, файл
  шаблона) валидируется на границе (`SEC-004`, `schemaguard`); линтер читает только имена/пути,
  содержимое файлов проекта не читает; монтирование `:ro`.
- **Документирование (`GO-014`)**: package comment у каждого пакета (`DOC-001`), doc comment у
  exported-сущностей с имени и назначения (`DOC-002`/`DOC-003`/`DOC-004`). `ExampleXxx` не
  обязательны (CLI без публичного API — исключение `GO-014`).
- **Стиль, именование, модернизация (`GO-001`, `GO-002`, `GO-004`, `GO-008`, `GO-009`, `GO-010`,
  `GO-017`)**: удерживаются инструментальным гейтом — `gofmt`, `go vet`, `golangci-lint`,
  `go test -race`.

## Risks / Trade-offs

- **Слабая модель передаёт неверный id эталона** → `list-templates` + `--template auto` + ошибка
  вызова с кодом `2` и перечнем допустимых.
- **Расхождение схемы и кода вердикта** → тест сериализует вердикт и валидирует его по
  `verdict.schema.json` в CI.
- **glob/regex по крупному дереву — производительность** → один проход обхода в снимок, правила
  применяются к снимку в памяти; для v1 объёмов достаточно.
- **Разметка слоёв путями ≠ реальные зависимости** → явно вне скоупа (proposal); документируется,
  чтобы не создавать ложного ощущения архитектурной проверки.
- **Секреты проекта в обходе ФС** → линтер читает только имена/пути (снимок дерева), содержимое
  файлов не читает; монтирование `:ro`.
